# 评分 run 取消后旧人工任务可复活：独立反证与预裁决

**建议裁决：P1，高优先级确认缺陷。** 当前生产 HTTP／PostgreSQL 路径允许具备 `review:manage` 的管理员将已取消评分 run 所属的 `review_task` 重新分配；具备 `review:work` 的被分配阅卷员随后正常提交。结果是该旧 run 从 `cancelled` 变为 `completed`，并新增一条 `is_current=true,status='confirmed'` 的 `question_grade`。这违反了取消的终态语义和成绩来源边界。此处需要管理员、阅卷员的合法身份；不是未认证越权。高优先级来自成绩完整性和可进入后续定稿的影响，而非权限绕过。

## 生产链与现有保护

1. **取消入口有权限，但终态明确。** [`server/routes_grading.go:28`](../../services/api-gateway/internal/server/routes_grading.go) 用 `grading:manage` 包装 `/scoring-runs/{runId}/cancel`。[`grading/handlers.go:342`](../../services/api-gateway/internal/grading/handlers.go) 先调用 `BeginScoringRunCancellation`，取消活跃的 OMR runtime task，再调用 `FinalizeScoringRunCancellation`。[`grading/scoring_run_lifecycle.go:63`](../../services/api-gateway/internal/grading/scoring_run_lifecycle.go) 在一笔事务中使 OMR run 失效，将未完成 review task 改为 `cancelled`、清除分配和 claim、增加 revision，并将评分 run 设为 `cancelled`、`review_count=0`（第 91–100 行）。因此旧人工任务应停止。
2. **分配入口验证管理身份、目标阅卷员与 revision，却缺少取消状态。** [`server/routes_review.go:45`](../../services/api-gateway/internal/server/routes_review.go) 要求 `review:manage`；[`review/handlers.go:170`](../../services/api-gateway/internal/review/handlers.go) 还检查 `reviewManagerScoped`、同租户活跃 grader。生产 [`review/store_postgres_tasks.go:190`](../../services/api-gateway/internal/review/store_postgres_tasks.go) 的 `UPDATE review_task` 只排除 `submitted` 和 `completed`（第 197–199 行），未排除 `cancelled`，也未连接所属 `scoring_run` 核验 run 状态。知道任务 ID 和取消后 revision 的管理员可令其重新变为 `assigned`。批量分配的第 213–236 行有相同状态条件。Memory Store 第 208–226、235–267 行同样允许。
3. **提交入口检查被分配人、任务状态和 revision，但没有 run 终态检查。** [`server/routes_review.go:49`](../../services/api-gateway/internal/server/routes_review.go) 要求 `review:manage` 或 `review:work`。[`review/store_postgres_tasks.go:257`](../../services/api-gateway/internal/review/store_postgres_tasks.go) 锁任务后验证 `AssignedTo`、`canSubmit` 与 revision（第 267–287 行）；重新分配后的 `assigned` 正是 [`review/store_memory.go:1040`](../../services/api-gateway/internal/review/store_memory.go) 所列可提交状态。该事务插入 `human_grade`，对单评任务将同答题块先前的 current `question_grade` 置为 superseded，再插入带原 `scoring_run_id` 的新 current confirmed `question_grade`（第 296–337 行），最后把任务设为 `submitted`。没有检验 run 是否已取消。
4. **提交直接改写被取消的 run。** [`review/store_postgres_tasks.go:352`](../../services/api-gateway/internal/review/store_postgres_tasks.go) 的 `UPDATE scoring_run` 通过任务的 `scoring_run_id` 关联 run，不限制 `sr.status`，并在 `queued_count=0`、更新后 `review_count=0`、`failed_count=0` 时设为 `completed`。取消步骤已把 `queued_count` 和 `review_count` 归零，单个任务提交即可满足条件。另一个 [`grading/scoring_run_lifecycle.go:197`](../../services/api-gateway/internal/grading/scoring_run_lifecycle.go) 的 `refreshScoringRunTx` 明确对 `cancelling/cancelled` 提前返回，但这条保护并未用于人工提交事务。
5. **数据库约束不足以挡住跨状态跳转。** [`migrations/000038_story056_scoring_recovery.sql:1`](../../services/api-gateway/migrations/000038_story056_scoring_recovery.sql) 的两个 `CHECK` 只限定 scoring run 和 review task 各自允许的状态值，并不约束 `cancelled → assigned` 或 `cancelled → completed` 的转换。[`migrations/000036_story056_grading_workbench.sql:233`](../../services/api-gateway/migrations/000036_story056_grading_workbench.sql) 的外键只保证 `question_grade.scoring_run_id` 指向同租户存在的 run；第 245 行的唯一索引只保证同答题块最多一个 current grade，不能保证其 run 未取消。

## 显式恢复与下游影响

未见对**被取消评分 run／旧 review task** 的显式 `reopen` 或 `resume` HTTP 入口。`retry-failed` 仅面向失败的 OMR，且 [`grading/scoring_run_lifecycle.go:155`](../../services/api-gateway/internal/grading/scoring_run_lifecycle.go) 明确拒绝 `cancelling/cancelled`。[`grading/scoring_readiness.go:59`](../../services/api-gateway/internal/grading/scoring_readiness.go) 将未取消的 run 视为活跃并阻止再启动；取消后可走新评分 run。这与“恢复旧已取消任务”的语义不同。管理端取消确认文字明确说“未完成的自动处理和人工任务将停止”，见 [`ExamScoringPanel.tsx:60`](../../apps/web-admin/src/features/grading/workbench/components/ExamScoringPanel.tsx)。因此不能把通用 `assign` 解释为已设计的取消恢复流程。

新 current grade 本身已被隔离数据库复现证实。进一步的源码影响是：[`score/store_postgres.go:455`](../../services/api-gateway/internal/score/store_postgres.go) 的 `FinalizeExam → createFinalsFromHumanTx` 从 `submitted/completed` 的单评任务及其 `human_grade` 建立 `final_grade`，没有排除已取消 run；因此该记录可成为后续定稿输入。若此答题块另有 current question grade，人工提交还会将它 supersede（[`review/store_postgres_tasks.go:324`](../../services/api-gateway/internal/review/store_postgres_tasks.go)），即旧 run 可能影响新 run 的当前评分事实。**本次复现未实际执行成绩定稿或发布**；公开成绩受影响的最终闭环仍待对应发布路径复核，不能写作已复现。

## 独立证据与严重度边界

- 我先按现行生产源码核对上述入口、权限、SQL、迁移，再读取主控提供的诊断用 [`review_cancel_repro_test.go`](review_cancel_repro_test.go) 与 [`repro-cancelled-run.log`](repro-cancelled-run.log)。诊断在隔离 PostgreSQL 17、生产 router、全量迁移和合成 fixture 下执行：取消 HTTP 200 后数据库任务为 `cancelled`，管理员 `assign` HTTP 200，grader `submit` HTTP 201，最后 run=`completed` 且 current confirmed question grade 数量为 1。日志中的 `PASS` 表示测试**成功观察缺陷**，不表示业务行为正确。我未运行或重跑该测试。
- 触发需合法管理员与阅卷员、已取消 run 中尚未完成且关联 `scoring_run_id` 的人工任务、该任务当前 revision；不证明普通 grader 能自行复活任务，也不证明发布门禁必然通过。
- P1 优于 P2：取消本是显式停止未完成评分，现可通过常规受权 HTTP 请求逆转，写入 authoritative current grade、使终态 run 变为 completed，并让旧任务的分数进入定稿来源。这是成绩事实和审计状态不一致，且可在真实生产数据库发生。若只按“是否无需授权即可触发”衡量会低估学校成绩完整性影响。尚未证明已发布成绩被直接改写，故不标 P0。
