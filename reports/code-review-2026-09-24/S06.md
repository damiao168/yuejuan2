# S06 — 成绩、发布、申诉、重评与报告

## 结论

确认 1 项已发布学生报告仍读取未绑定到发布成绩的“最新 AI／人工反馈”问题。证据为当前 SQL、发布快照及可写入调用链；本轮未连接运行时数据库进行端到端复现。成绩本身仍来自已发布的 `final_grade`／`submission_grade`，但反馈和错因线索可在发布后漂移。

## 发现

### S06-F01 — 已发布报告把最新 AI／人工反馈拼到冻结的 final grade 上

- **优先级：P2。** 发布后学生看到的题目分数与评语可能不再来自同一评分版本，削弱发布快照的一致性。
- **位置／生产入口：** `services/api-gateway/internal/report/store_postgres.go:160-195` 以已发布且 locked 的 `submission_grade` 和 `final_grade` 作为报告基础，但两个 lateral 查询分别按 `answer_segment_id` 选 `ai_grade` 最新 succeeded 记录（`:179-185`）和 `human_grade` 最新记录（`:186-192`），没有关联 `final_grade.source`、对应 AI/human grade ID、release ID 或发布时间。`report/stats.go:37-43,46-58` 将其转换为学生可见的 AI feedback、teacher feedback 和 error clues。学生入口为 `server/routes_release.go:63`；`report/handlers.go:22-42` 允许学生读取本人报告。
- **触发条件：** 考试已发布后，具有 `grading:manage` 的租户／学校管理员对旧 answer segment 创建新的 AI grade（`server/routes_grading.go:31`；`subjective/handlers_grade.go:32-64,168-178`），或创建并提交新的单评任务。报告查询每次重新读取最新的 AI/human 行，而 final grade 仍是已发布版本。
- **后果：** 学生可能看到新 AI 建议中的反馈／错因、或新人工评语，搭配旧版已发布分数；这些内容未经过该考试成绩发布门禁和 release snapshot 校验。调用者须有管理阅卷权限且仍受 tenant／资源边界约束；这不是跨租户读取问题。
- **证据：** 发布成绩包含 immutable release snapshots：`services/api-gateway/migrations/000088_storyA18_score_releases.sql:136` 的 trigger 拒绝修改已发布 release snapshot；`scorerelease/store_postgres.go:941-952` 从 release item/question 快照读取 `source_id` 与 explanation。当前 report lateral 查询没有使用该绑定。人工 task 提交会插入 human_grade（`review/store_postgres_tasks.go:257-305`）；subjective grade 生产路径调用 `CreateGrade` 持久化 AI grade（`subjective/handlers_grade.go:168-178`）。
- **限制：** 由于任务要求只读，未运行现场复现。静态路径证明报告查询可能混用版本；要将影响验证到具体考试／角色仍需隔离 Postgres E2E。
- **修复方向：** 报告 feedback 应随已发布 release 固化，并通过 `score_release_question.source_type/source_id` 或正式反馈快照关联到同一来源；如果产品允许发布后更新评语，应要求形成新 release，不能静默取最新 grading row。
