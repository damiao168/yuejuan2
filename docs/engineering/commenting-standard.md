# 代码注释与维护说明标准

本标准适用于本仓库后续开发、修复、评审和维护。目标是让维护者理解代码的职责、设计原因、业务限制和失败后的处理方式。全仓检查按文件记录结果；并非每个文件、函数或代码行都需要新增注释。

## 1. 基本要求

1. 注释必须与当前实现、调用关系和测试一致。看不懂时先核实，不能猜测或承诺代码没有保证的能力。
2. 新增维护注释使用简单中文，标识符、协议名称和工具指令保留原文。一句话讲一件事，避免口号和空泛的“确保安全”“提高性能”。
3. 优先解释原因、前提、边界和误改后果。类型与函数名已表达的信息不用重复。
4. 注释放在规则真正执行的位置附近。跨模块背景集中写在模块文档，调用处按需引用；不复制多份长说明。
5. 代码修改时同步检查相关注释和文档，过时注释应更新或删除。没有必要说明的代码可以没有注释。
6. 既有准确的英文注释可以保留。修改相关逻辑时可统一润色为中文，不为语言统一做无价值翻译。

推荐句式：**触发条件 → 处理约束 → 原因或后果**。例如：

```ts
// 请求返回前可能已切换账户；旧账户的结果不能修改新账户的缓存和任务列表。
```

避免：`// 判断用户是否相同`、`// 遍历列表`、`// 调用接口`。这些只是重复语句。

## 2. 必须说明的维护点

| 情况 | 注释应回答的问题 |
| --- | --- |
| 业务状态转换 | 谁能执行？哪些状态允许？哪些事实已经冻结？ |
| 租户、学校和身份隔离 | 身份从哪里取得？作用域由谁验证？维护任务有什么例外？ |
| 数据库事务、锁和版本号 | 哪些操作必须一起完成？防止什么竞争？失败时是否回滚？ |
| 幂等、重试和任务租约 | 什么标识代表同一操作？何时能重试？过期结果为什么要丢弃？ |
| 网络与本地持久化 | 顺序为什么不能交换？远端成功而本地失败时保留什么事实？ |
| 异步界面更新 | 请求属于哪个用户、任务和版本？ref 与 state 分别负责什么？ |
| 算法、阈值和坐标 | 单位、取值域、坐标原点、边界和依据是什么？未知情况如何处理？ |
| 模型输出 | 哪些只是建议？证据、版本及人工复核要求在哪一步执行？ |
| 备份、恢复及破坏性操作 | 校验与变更的边界在哪？异常后是否恢复服务？影响哪些资源？ |
| 特殊兼容代码 | 对应什么已知限制？什么条件下可以去掉？ |
| 非直观的测试场景 | 如何触发故障？测试保护哪条业务规则？ |

不要把“检查过权限”写成“所有访问都安全”，不要把“先查询再写入”写成“并发只执行一次”。注释必须准确限定保证范围。

## 3. 篇幅与放置

| 位置 | 通常篇幅 | 要求 |
| --- | --- | --- |
| 复杂包/模块入口 | 3–8 行，集中写一次 | 职责、关键流程、边界；避免各文件重复模块介绍 |
| 复杂文件顶部 | 2–5 行 | 仅在职责或数据来源不直观时添加；不得只翻译文件名 |
| 对外或跨模块函数 | 2–6 行 | 非直观前提、返回含义、副作用、特殊失败；简单接口可更短 |
| 关键分支与步骤 | 1–3 行 | 写在相关语句上方，说明规则及原因 |
| 复杂字段和常量 | 1–2 行 | 单位、空值含义、来源或作用域；明显字段不逐个注释 |
| 复杂测试 | 2–4 行 | 场景与保证；不逐句解释 mock/render/expect |

简单文件可能新增 0–3 处，普通业务文件约 3–8 处，复杂文件约 6–12 处。这些只能用于估算，不能作为配额或验收指标。已有好注释可满足要求。不要规定注释率；注释超过约十行时，考虑把背景移到模块文档，保留核心约束和相对链接。

## 4. 语言和文件约定

### Go

- 包级说明用 `// Package 包名 ...`，通常集中在 `doc.go` 或主要入口。
- 对外符号的文档注释以符号名开头。说明错误、事务归属及调用方责任，不机械罗列参数类型。
- SQL 字符串的维护说明写在 Go 代码旁，不向运行 SQL 字符串注入文字。
- 保留 `//go:`、构建标签、生成指令、许可证等特殊内容及其位置。

```go
// BootstrapInitialAdmin 创建首次部署所需的平台管理员。
// 仅接受平台租户和平台管理员角色；已有启用的管理员时拒绝初始化。
```

### TypeScript、JavaScript、React

- 复杂公开接口用 JSDoc；局部原因用 `//`。类型已说明的参数不重复写 `@param`。
- ref、effect、缓存和异步 guard 说明各自防止的错误；不得为消除 lint 提示而编造理由或改变依赖。
- JSX 中只注释不直观的交互、权限展示或布局约束，避免每个组件前写标题。
- 保留 `@ts-*`、eslint/biome 指令、纯函数标记、打包器魔法注释及 source map 指令。

### Python

- 新开发的公共模块、类、函数可使用简短 docstring；参数有单位、特殊错误或资源责任时再展开。
- 批量“只改注释”任务优先使用 `#`，因为 docstring 是运行时可读内容，不能默认等同于无行为变化。
- 模型提示词、SQL、正则和测试输入中的字符串不是注释，不得当作注释润色。
- 保留 shebang、编码声明、类型检查与覆盖率指令。

### Rust

- 模块说明用 `//!`，对外接口用 `///`，局部原因用 `//`。
- 持久化、锁和资源所有权接口说明调用前提与错误。仅在适用时写 `# Errors`、`# Panics`、`# Safety`，不套空模板。
- 现有文档测试与代码属性保持有效；新增可执行示例须验证。

### PowerShell、Shell、Docker、YAML、CSS

- 运维脚本说明输入边界、影响范围、顺序、失败恢复；PowerShell 的完整命令帮助按需使用 `.SYNOPSIS` 等格式。
- 配置说明合法值、单位、适用环境和配置之间的关系；不粘贴真实凭据。
- CSS 只说明打印尺寸、坐标对应、层叠或兼容限制，普通颜色和间距不逐条解释。
- 不把注释插入命令续行、here-string、YAML 块标量或 Docker RUN 命令中；先确认语法及执行边界。

### SQL、JSON、提示词和生成文件

- 已存在的历史迁移按内容哈希校验，不直接加注释。业务说明放在数据库维护文档并引用迁移号。
- 新迁移在首次应用前说明业务约束、存量处理、执行顺序。`COMMENT ON` 会改数据库元数据，属于迁移行为，不属于纯注释。
- JSON/JSONL/锁文件/快照/数据集不插入注释或额外字段；必要解释使用旁置文档。
- `packages/sdk/src/generated/` 等生成产物不手改。需要接口文档时修改权威源或生成模板，并走正常生成和契约检查流程。
- 提示词 Markdown、模型配置及带哈希的内容属于运行输入；解释写在旁置文档，改变原文需独立评审及对应测试。
- 第三方代码、缓存、构建产物和二进制不纳入源码注释修改。

## 5. 测试、TODO 与文档维护

- 测试名能完整说明场景时不再重复；复杂时序说明动作先后和保护的结果。模拟结果不能描述成生产集成保证。
- TODO 写具体待办、触发条件及有效追踪入口；没有追踪编号时不编造编号，不把未知行为写成已知保证。
- 不保留整段注释掉的旧代码。作者、日期和逐次修改记录交给 Git。
- 模块说明链接使用仓库相对路径；不要写维护者本机绝对路径或容易漂移的固定行号。
- 隐私、安全或合成数据约定按所在目录规范执行，包括 `lab/AGENTS.md`。

## 6. 逐文件实施与验收

每次全仓整理先保存工作区基线，保留已有未提交修改；将维护中的未跟踪源码纳入清单。按目录分工，避免多个维护者同时写同一文件。

文件清单使用以下状态：

- `pending`：尚未完成审读，不能计入完成。
- `annotated`：已审读并补充/修订必要注释，记录具体维护点。
- `existing_sufficient`：已审读，现有注释足以说明非直观规则。
- `self_explanatory`：已审读，代码及测试名称清楚，无必要新增。
- `protected`：生成、哈希保护、运行输入或数据等，记录不直接修改的原因。
- `documentation`：说明性文档，使用正文维护，不插入“代码注释”。
- `excluded`：依赖、输出、临时资源、二进制等，记录排除原因。

审读需结合函数体、调用和测试；自动枚举只能帮助盘点，不能把“匹配了文件名”当作理解。若只读了部分，仍为 pending，直到该文件的必要维护点都已检查。不要批量生成与内容无关的文件头凑覆盖率。

每批验收：

1. 每条新增注释都有实现依据，解释原因或边界，没有夸大保证。
2. 文件级清单与实际改动一致，未读项明确保留 pending。
3. 使用相对工作区基线的比较；尽可能核对去掉普通注释后的 token/AST 不变。保留换行语义、指令、字符串及受保护内容。
4. 执行适用的语法、类型、格式和现有测试门禁；纯注释不必新增镜像实现的测试。若工具把文档注释纳入产物，应按对应产物验证。
5. 发现业务缺陷单独报告和修复，不能混入注释批次。全仓已有的无关变化不回退、不覆盖。

评审者最终应能回答：**这里为什么这样写？哪些条件不能破坏？失败以后怎么办？** 以这些问题是否清楚作为标准，不以注释行数或百分比作为标准。

## 7. 今后开发的交付要求

本标准是仓库开发要求，适用于今后新增和修改的业务代码、接口、脚本、配置及测试，由根目录 `AGENTS.md` 引用执行。

1. 开发者先核对实现、调用关系和相关测试，再为第 2 节列出的非直观规则补充必要注释。简单代码已经表达清楚的内容，无需再写一遍。
2. 注释随对应代码一起交付。修改行为时，同步更新或删除附近已经不准确的注释；不要留待下一轮全仓整理。
3. 交付前检查注释是否简单直白、与实现一致，是否说清关键前提、边界和失败处理。已有准确说明不重复添加，受保护文件仍按第 4 节处理。
4. 评审必须检查上述要求。关键规则缺少说明、注释与代码矛盾或夸大保证时，应在本次变更中处理完再交付。评审以信息是否有用为准，不用注释数量或比例代替判断。
