# 学校成员资料编辑

学校管理的三个入口使用 `org:manage` 和现有学校数据范围。列表直接提供编辑操作，保存失败时保留填写内容。

| 入口 | 可修改内容 | 接口 |
| --- | --- | --- |
| 学生管理 | 姓名、学号、性别；原有停用/恢复仍保留 | `PATCH /api/v1/students/{id}` |
| 年级与班级 | 年级名称；班级名称、班级代码 | `PATCH /api/v1/grades/{id}`、`PATCH /api/v1/classes/{id}` |
| 人员与权限 | 姓名、教职工号、新手机号 | `PATCH /api/v1/users/{id}/profile` |

学生转班使用独立的“调整班级”，调用已有 `PUT /api/v1/students/{id}/enrollment`，保留原班学籍。资料补丁不允许直接修改班级或学校。年级、班级编辑不改变学年、届别或父级关系，避免把既有学生和考试范围整体迁移。修改班级代码后，后续 CSV 导入应使用新代码；已有班级引用仍使用原记录 ID。

学号在同校内、班级代码在同年级内、手机号和教职工号在同租户内查重。重复返回 409。学生补丁仅修改提交的字段；性别空串表示清空。未知字段、空补丁和非法枚举返回 400。

人员基本资料保存沿用近期认证要求，并核对管理员是否能管理目标的全部角色和学校，不允许在此修改本人账号。工作职责和班级仍由“更多 → 职责与班级”单独调整，不随资料修改。

人员弹窗只展示脱敏手机号；新手机号留空时不提交，保留原号码。工号可清空，稳定用户名保持原值。请求提交打开时的姓名、工号、手机号掩码作为旧值核对；两个号码掩码相同的变化不能由这一核对发现。资料冲突返回 `managed_user_profile_conflict`，不能自动重试覆盖。

人员手机号或工号实际变化时，资料、安全版本、会话和设备撤销、恢复及激活链接作废在同一事务中提交。响应的 `login_identity_changed` 表示实际身份变化；启用人员需重新登录，待激活人员需重新生成邀请。仅改姓名保留原凭据。接口响应和审计均不返回完整手机号。

学生名册上方直接显示“在籍／已停用／全部”。停用只改变状态，切到“已停用”后可恢复；恢复沿用原学生 ID、学号、班级和历史业务记录。

停用学生的“更多 → 彻底删除”调用 `DELETE /api/v1/students/{id}`，要求 `org:manage`、学校数据范围及近期认证。确认弹窗显示姓名和学号，明确提示删除无法恢复。仍在籍返回 `student_must_be_inactive`（409），有关联返回 `student_in_use`（409），不存在返回 404。

彻底删除是物理删除学生及其学籍，不级联删除考试快照、考勤、打印身份、答卷、成绩或申诉。历史和软删除的业务引用也会阻止删除；学生账号的 JSON 作用域另行检查。学生行锁保护状态与外键引用检查，学籍和名册在同一事务中删除，外键冲突或写入失败时回滚。接口保留删除审计的目标 ID。MemoryStore 仅存储名册，不模拟跨模块引用；正式运行的引用约束由 PostgreSQL 执行。
