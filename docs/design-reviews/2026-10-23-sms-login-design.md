# 用户名、微信与手机验证码登录方案

状态：待接入实现。当前没有确定短信供应商，本次只交付设计；不添加模拟发送、固定验证码或看似可用的手机登录入口。

## 现有能力与目标

管理端已有用户名密码和微信二维码登录。密码请求继续使用 `identifier`，服务端保留用户名、手机号和教职工号别名兼容。已有 `phone_normalized` 是人员资料和密码登录别名，不能据此认定号码已由本人验证。

接入后，登录页提供“用户名密码”“微信扫码”“手机验证码”三种方式。短信验证码用于登录已激活且本人验证绑定的现有账号，不自动注册、激活邀请、改密或赋予角色。短信登录不作为更高认证等级的证明，也不替代既有关键操作的近期认证要求。

关联实现：[登录页](../../apps/web-admin/src/pages/LoginPage.tsx)、[登录接口](../../services/api-gateway/internal/auth/handlers.go)、[身份归一化](../../services/api-gateway/internal/auth/identity.go)、[资料变更与凭据撤销](../../services/api-gateway/internal/auth/managed_profile_store.go)。

## 学校选择与前端交互

- 专属学校链接沿用 `tenant_hint`；全局入口先填写学校代码。三种方式共享同一学校上下文，不通过手机号查询或展示其所属学校列表。
- 服务端解析学校后校验该租户的能力。新增拟议 `GET /api/v1/auth/login-methods?tenant_hint=...` 或 `?tenant_code=...`，只返回可用方式，例如 `{"methods":["password","wechat"]}`；学校未知时不返回学校或账号详情。
- 供应商未配置、租户未启用或全局停用时，不返回 `sms`，前端不显示手机标签；客户端伪造请求仍返回 `sms_login_unavailable`。已打开手机标签后能力失效，提示“手机登录暂不可用，请使用其他方式”。
- 手机表单显示学校、手机号、验证码、获取验证码按钮和设备选项。发送后按服务端 `retry_after_seconds` 倒计时；刷新页面不能绕过服务端限流。沿用公共电脑与常用电脑互斥规则。
- 切换学校、手机号或登录方式后清空原挑战与验证码；忽略之前异步发送/登录请求的回执。发送提示统一为“如该手机号已绑定可登录账号，验证码将发送至该手机”，不承诺短信已送达。

## 供应商接口与平台配置

API Gateway 中增加供应商适配层，业务服务只依赖以下接口；先选择一家真实供应商实现，后续增加适配器无需改变登录协议。

```go
type SMSProvider interface {
    Send(ctx context.Context, request SMSSendRequest) (SMSSendReceipt, error)
}

// RequestID 是发送去重键；适配器必须说明供应商是否支持该键的幂等保证。
type SMSSendRequest struct {
    RequestID string
    PhoneE164 string
    TemplateID string
    Code string
    ExpiresInSeconds int
}

// Accepted 仅表示供应商受理；不能据此宣称手机已收到短信。
type SMSSendReceipt struct {
    Accepted bool
    ProviderMessageID string
}
```

平台管理员未来在“平台设置／短信服务”配置供应商类型、账号标识、密钥引用、地区、签名、登录/绑定模板 ID、启用学校范围和日发送预算。密钥只保存在服务端密钥存储或既有加密配置中，前端只返回“已配置”和掩码，不回显密钥。保存、试发、启停需复用平台权限、近期认证和审计；审计不包含完整手机号、验证码或密钥。

保存配置只做格式与凭据访问校验；“发送测试短信”是单独操作，输入明确测试手机号，受同等限流并记录真实供应商请求结果。只有配置完整、真实试发验收通过且租户被启用后才开放手机入口；配置中记录验证时间和所验证版本，换密钥、签名或模板后重新验收。无供应商时默认关闭，不配置静默成功的空实现。

## 手机号验证绑定与存量处理

新增迁移记录绑定事实，例如 `auth_phone_binding(tenant_id,user_id,phone_normalized,verified_at,version,revoked_at)`，租户内有效手机号唯一。保留人员资料字段，避免把历史录入号码自动标为已验证。挑战记录归属租户，并沿用项目租户隔离和最小运行权限。

本人以密码或已绑定微信登录后，在账户安全页发起绑定；需先完成现有近期认证，再接收并校验该号码验证码。验证码通过时，在账户锁内核对预期资料/绑定版本、写入验证事实、同步手机号、递增安全版本并撤销旧会话、可信设备及未使用恢复凭据；提交成功后要求重新登录。号码已属于其他账号时不能迁移或合并身份。

管理员录入或修改人员手机号只产生未验证资料，不产生验证事实。号码变化须在同一事务撤销旧绑定和旧验证码挑战，并复用已有凭据失效链路；修改姓名或教工号不改变号码验证归属。新增绑定表后，手机号资料修改必须同步此规则，不能只改 `phone_normalized`。本人换号需要近期认证、新号验证和版本检查；无法登录的用户继续通过现有管理员协助恢复流程核对身份，不能用一个未验证号码直接找回账户。

## 拟议 API 与状态

所有挑战接口返回 `Cache-Control: no-store`，验证码只通过请求体提交。示例路径均为拟议契约，实施时同步 OpenAPI、SDK 与契约门禁。

| 请求 | 输入 | 成功响应与约束 |
| --- | --- | --- |
| `POST /api/v1/auth/sms/challenges` | `tenant_code` 或 `tenant_hint`、`phone`、客户端随机 `request_id` | `202 {challenge_id,challenge_token,expires_at,retry_after_seconds}`；只给该学校内有效验证绑定且 active 的账号实际发送，对未知、未绑定或停用账号返回同形不可登录挑战，避免泄露账号状态 |
| `POST /api/v1/auth/sms/session` | 学校上下文、`challenge_id`、`challenge_token`、`code`、`remember_device`、`public_device`、`device_name` | 验证后复用既有会话签发，设置 HttpOnly Cookie，返回现有 `LoginResponse`；不在 JSON 返回浏览器令牌 |
| `POST /api/v1/auth/phone-binding/challenges` | 已登录且完成近期认证；`phone`、`request_id`、预期绑定版本 | `202`，返回同类挑战；用途固定为绑定并绑定当前用户，不能换作登录凭据 |
| `POST /api/v1/auth/phone-binding/complete` | 已登录且完成近期认证；`challenge_id`、`challenge_token`、`code`、预期绑定/资料版本 | 事务内消费挑战并更新绑定，撤销旧凭据后返回需重新登录的结果；版本变化返回冲突，不覆盖并发修改 |

`challenge_token` 使用至少 256 位随机值，服务端只存摘要；它约束当前发起方，不能用可枚举的挑战 ID 尝试他人验证码。挑战保存租户、用途、用户 ID（真实绑定时）、号码摘要、绑定版本、安全版本、过期时间、失败次数、发送状态和消费时间。六位数字验证码使用密码学随机数生成，保存服务器密钥 HMAC 摘要，摘要输入包含租户、用途、挑战 ID 和验证码；短验证码不能只做无密钥哈希。

状态为 `pending_send → accepted → consumed`，另有 `send_failed`、`delivery_unknown`、`expired`、`invalidated`。先持久化待发送挑战，再调用供应商；确认受理后才允许验证码校验。超时不能自动视作已发送或重试成功；标为 `delivery_unknown`，前端提示稍后重新获取。只有供应商明确支持去重时，才允许相同请求 ID 重试真实发送；同请求 ID 重放返回原挑战，不能重复扣费或延长有效期。重新获取时生成新挑战，事务内废弃同租户、号码、用途的旧挑战。

消费验证码与创建会话在同一数据库事务内完成，锁定挑战和账户，检查用途、令牌摘要、有效期、剩余次数、学校、active 状态、验证绑定及安全版本。并发提交只有一个能消费；会话写入失败则回滚消费。停用、换号、改密后，旧挑战不能创建会话。会话创建仍走现有组织范围、风控、设备和会话策略，不能因为短信成功跳过这些校验。

## 默认有效期、限流与失败恢复

以下为实施初值，平台可在服务端约束范围内调低，不能由客户端覆盖：

| 规则 | 初值 |
| --- | --- |
| 验证码有效期 | 5 分钟，以签发时间为起点，供应商等待不续期 |
| 同租户、号码、用途重发间隔 | 60 秒；只保留一个最新有效挑战 |
| 每挑战校验失败次数 | 5 次后永久失效；发送新码不清空账号和来源层计数 |
| 每号码发送量 | 每小时 5 次、每天 10 次；跨租户再有每天 20 次的号码总量上限 |
| 每来源发送量 | 每 IP 每 10 分钟 20 次、每天 100 次，另保留平台日预算和紧急停用开关 |
| 登录校验限流 | 复用既有用户 ID、来源、标识/来源三层限速，并增加挑战桶 |

手机号先走现有 E.164 归一化再计数；号码/IP 桶键用服务端 HMAC，日志只保留掩码和请求关联 ID。发送层跨实例使用 Redis 原子计数；Redis 不可用时短信发送与验证码登录关闭，不能退化为每进程独立额度。返回 `429` 和 `Retry-After`；错误码区分服务不可用、发送受限、挑战无效，前端无需展示供应商内部信息。挑战无效统一覆盖错码、过期、被消费、绑定变更和账号不可登录，避免进一步探测状态。

供应商拒绝、预算耗尽、超时或回执异常不得签发会话。发送失败不把用户标为已验证；失败和未知结果仍计入短时防刷配额，预算结算按真实受理回执核对。验证码/挑战令牌不写浏览器持久存储、分析事件或日志。过期挑战按既有保留策略清理，供应商消息 ID 只用于对账；到达回执不影响手机号所有权或验证码有效期。

## 实施与验收顺序

1. 完成数据迁移、供应商接口及单个真实适配器、平台配置、发送预算与能力接口；未配置及故障状态下确认入口隐藏、接口拒绝且无短信费用。
2. 实现本人验证绑定和资料变更撤销，再实现验证码登录；以隔离 PostgreSQL/Redis 验证消费与会话原子提交、并发只成功一次、重发使旧码失效、换号/停用/改密使在途挑战失效。
3. 接入第三个登录标签，验证学校隔离、切换学校/号码时旧回执丢弃、公共电脑选项、倒计时与断网恢复。保留用户名密码和微信回归，未知手机号不得创建账号。
4. 选定供应商后，用授权测试号码完成真实发送、模板签名审核、到达率/时延、失败/超时、请求去重、费用对账和紧急停用验收。测试替身只能证明接口逻辑，不能代替真实短信验收。
5. 先对试点学校开启能力，观察发送失败率、限流命中、预算和登录成功率；出现异常关闭短信能力，用户继续用既有登录方式。未完成真实供应商验收前维持关闭。
