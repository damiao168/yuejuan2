## 2. 已复现的问题及修复边界

桌面原先的故障是：评分已成功并推进任务版本，但响应丢失；重启后加载原草稿，再同步只做版本预检，于是显示冲突。测试没有发现第二次评分 POST，因此本轮不把它描述为已证实的重复评分漏洞。

新恢复字段 `submissionCommand` 是加密正文中的可选字段。旧草稿仍可读取，在第一次同步时附加命令；没有修改数据库 schema、历史 SQL、锁文件或生成 SDK。字段包含服务器、租户、用户、任务、稳定 ID 和冻结载荷，不保存访问令牌。恢复会核对命令、操作、任务以及成功结果。普通 submit 和服务端已有盲测 seed-submit 均接受统一任务结果，不展示参考分。

旧会话发出的请求仍可能已在服务端成功。客户端在每次 await 后和新写请求前检查会话，并保留原事实供恢复；不能承诺取消网络请求就撤回评分。Web 当前窗口的认证/命令保护不等于跨标签 Cookie 原子切换；桌面浏览器开发回退也不具备跨标签数据库事务。

最终独立复核发现并补修了范围重置的边界：同账号绑定新会话代次后，旧实现只清空队列而没有重新加载；外层 `runAction` 抑制迟到提示也不能阻止动作体继续写入。已复现旧领取结果插入新考试、旧暂放结果清空新题选择，以及旧数学请求解除新考试操作锁。修复在动作执行位置检查范围，不用通知是否出现来代替业务状态验证。

## 3. 性能证据

开始修复前保存了 825 个源码/配置文件的 SHA-256 和内容，位于 `output/frontend-improvements-2026-10-04/baseline`。另为 E2E 的 3 个待改文件保存了 `baseline-e2e`。这些是保留现有未提交修改的快照，不是全仓已审读证明。

为避免误用旧 dist，已从源码快照重新构建 Web，并用相同测量脚本计算 HTML 入口、modulepreload、静态 import/export 的依赖闭包。gzip 是每个文件分别压缩后相加，不是浏览器加载时间。

| 指标 | 源码基线新构建 | 本轮最终构建 |
| --- | ---: | ---: |
| 首屏 JS 原始字节 | 2,873,654 | 1,817,258 |
| 首屏 JS gzip 字节 | 876,365 | 560,179 |
| 首屏 CSS 原始字节 | 304,760 | 250,498 |
| 首屏 CSS gzip 字节 | 54,220 | 41,636 |

首屏 JS gzip 减少 316,186 字节，约 36.1%。Vite manifest 和实际静态依赖图用于区分首屏与动态模块。预算当前为 616,190 gzip 字节，以首次优化后实测 560,172 为基准留约 10% 增长余量，并阻止学校对话、公式、PDF 等命名 chunk 进入首屏。最终构建仍在预算内，不随每次构建小幅变化自动抬高阈值；阈值不是行业标准，新增功能应带实测理由调整。

仍有较大的 antd 和公式 chunk，构建会保留 500 KB 体积提醒。本轮没有提高告警阈值或盲目改 manualChunks；没有测量真实网络首屏时延、CPU Profile 或用户现场的五场景瀑布，不能据字节减少宣称交互时间提升 36.1%。

测量产物：`performance-source-baseline.json`、`performance-after.json`；旧 dist 线索另留 `performance-baseline.json`，不作为最终优化归因依据。均在 `output/frontend-improvements-2026-10-04`。
