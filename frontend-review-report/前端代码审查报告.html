1执行摘要

整体判断：这是一个工程质量明显高于行业平均水平的前端——TypeScript 严格、几乎无 any、无调试残留、错误与安全边界考虑周到、核心模块有清晰的关注点分离。当前的主要问题不在“代码脏”，而在架构一致性与复杂度管理：两套路由、两套数据获取范式并存，核心工作台状态与 props 过度膨胀，共享包利用率偏低。

P0
两套路由系统并存，TanStack Router 被“降级”为壳

依赖了 @tanstack/react-router，却只注册 5 个无组件的占位路由，真正的页面解析、权限、导航由自研 AppRoute 注册表 + pageRendering 完成。类型安全、loader、路由级代码分割等能力基本未用，还带来理解成本。

P0
核心阅卷工作台绕开 react-query，手写一整套缓存/预取/草稿队列

react-query 仅 11 个文件使用；最复杂的 GradingWorkbench 用约 30 个 state/ref + 自研队列、预取、冲突、续租逻辑。能力很强但状态机复杂、难测试，且与全站数据范式不统一。

P1
巨型组件与严重 prop drilling

20+ 个文件超过 18KB（最大 ScoringAssuranceWorkspace 46KB）；TaskRail 单组件接收 30+ props，WorkbenchTaskContent 接收三个十几字段的聚合对象。

P1
共享包“建了但用得少”，跨应用复制代码

packages/ui 仅约 6 处实际引用；design-tokens 在 TSX 中仅 2 处使用，另有 23 处硬编码色值；desktop-client 的 api/client、userError 与 web-admin 高度同源却各自复制演化。

P2
工程化与测试的“最后一公里”

Biome 规则集为 none 且 formatter 关闭；50 个全局 CSS 无 CSS Module；多个 feature（appeals / onboarding / calibration 等）单测为 0；teacher-portal 为空壳。

3做得好的地方

在提出改进前，先明确这些应当保持、并可作为规范推广到其余模块的实践。

严格的类型体系tsconfig 开启 strict / noUnusedLocals / noUnusedParameters / noImplicitReturns；全量代码几乎无 any，Biome 对 noExplicitAny 告警。
清晰的关注点分离grading 等核心模块把逻辑下沉为 14 个自定义 hook 与纯函数 model/presentation，组件负责组合与渲染。
周到的错误边界ErrorBoundary 用 resetKey（路由变化）复位而非 key，避免无谓重挂；并正确处理了 lazy 模块被拒绝后会被缓存的边界。
扎实的传输层安全统一处理鉴权、CSRF 头、写操作幂等键（Idempotency-Key）、428 二次认证事件、SSE 与 Blob 下载。
路由级代码分割pageRendering 中所有页面均通过 React.lazy 按需加载，主包不承载全部页面。
无调试残留、注释规范0 处 console.log、0 处 TODO/FIXME；关键业务规则、权限边界、并发与恢复均有简洁中文注释，符合仓库注释标准。
公共场景安全细节公共电脑模式含空闲锁定、解锁二次认证、离开清理；登出时 queryClient.clear 防止账号间数据残留。
具备自动化测试基建Vitest 单测 + Testing Library + Playwright E2E/视觉用例，核心链路（grading/exams/capture）覆盖较好。

6.1 路由与整体架构

P0收敛双路由：让 TanStack Router 真正工作，或移除它
证据
router/appRouter.tsx 仅 5 个路由且均无 component；真正渲染由 router/routes.tsx（24 生产 + 4 mock 的 AppRoute）与 router/pageRendering.tsx（16KB switch）完成。

当前等于同时维护两套路由心智模型：TanStack 负责“匹配 URL”，自研注册表负责“决定渲染谁、能否访问”。其类型安全路由、beforeLoad/loader、路由级代码分割、defaultPreload 等能力基本闲置。

建议：推荐把每个 AppRoute 映射为带 component 的 createRoute，权限/体验判断移入 beforeLoad，页面组件交给路由树做分割与预取，$experience 作为前缀或布局路由。若团队评估后坚持自研，则应删除 @tanstack/react-router 依赖与 RouterProvider，避免“装了却没用”误导后来者。
P1渲染函数体中的副作用：setBusinessCommandScope
证据
AppShell.tsx:41 在组件函数体直接执行 setBusinessCommandScope(user?.tenant, user?.id)。

渲染体应保持纯函数；直接在其中写模块级状态，在严格模式/并发渲染下可能以非预期顺序执行，且难以推断。

建议：移入 useEffect(() => setBusinessCommandScope(user?.tenant ?? "", user?.id ?? ""), [user?.tenant, user?.id])。成本极低，建议作为首批顺手项。
P1AppShell 职责过载，应拆分认证与引导
证据
AppShell.tsx（约 250 行）同时负责会话恢复、登录/登出、激活/恢复页、路由解析、experience 切换、导航。
建议：抽 AuthProvider + useAuth()（承载 user/loading/login/logout），激活/恢复抽为独立视图或真实路由，路由解析交还给路由层。AppShell 最终只保留“布局 + 当前路由出口”。
P2明确 Hash History 的取舍

使用 createHashHistory 利于纯静态托管（nginx.conf 已配套），但 URL 不美观、不利于服务端路由与未来 SEO。可保留，但建议在文档说明原因；若后续需要真实地址再切换为 browser history 并配置 fallback。

6.2 数据获取与状态管理

P0收敛数据获取范式：工作台回归 react-query
证据
react-query 仅 11 个文件使用；GradingWorkbench.tsx 含约 30 个 useState/useRef，并自研任务队列、预取（useGradingPrefetch）、草稿保存队列（TaskDraftSaveQueue）、冲突与续租。

这些手写逻辑覆盖了 react-query 已内置的能力（缓存、去重、分页/无限滚动、预取、失效、重试、后台刷新），使状态机非常复杂、难测试。客观上阅卷确有特殊业务（认领、续租、草稿冲突仲裁），但数据获取/缓存与业务规则应当分离。

建议：任务列表用 useInfiniteQuery、任务上下文/聚合用 useQuery（key 含 examId/taskId），提交分数用 useMutation 并做失效；草稿自动保存用 mutation + 轻量队列；认领/续租/冲突仲裁保留为薄业务层。可从“只读加载”部分先行迁移，写路径随后。
P2避免直接 import 全局 QueryClient，改用 hook
证据
GradingWorkbench.tsx:8 直接 import { appQueryClient } 并调用 invalidateQueries。
建议：组件内统一用 useQueryClient()；单例仅用于在入口挂载 Provider。这样测试可注入独立 client，也避免隐式全局依赖。
P2优先“派生状态”，减少镜像 state

部分 state 是由上下文/路由可直接计算的值的“副本”，容易出现不一致。建议能用 useMemo 从 ctx / route / user 派生的就不另存 state；确需本地编辑初值时，用 key 重置（如已有的 exam/account key 模式）。

6.3 组件设计

P1拆分巨型组件/文件
证据
20+ 文件超过 18KB：ScoringAssuranceWorkspace 46KB、QualityDashboardPage 35KB、PlatformModelConfigPage 32KB、ArbitrationPage 31KB、CaptureBatchPage 29KB 等。
建议：按“页面区域 + 职责”拆为子组件与 hook（数据获取、表现、事件各归位），建议单文件控制在约 250–300 行内；纯计算移入 model/presentation（grading 已是正面范例，可推广）。
P1消除 prop drilling：Context / 组合 / 状态收敛
证据
GradingWorkbench → TaskRail 传 30+ props；WorkbenchTaskContent 接收 answer/evidence/editor 三个十几字段的聚合对象。
建议：① 用工作台级 Context 下发共享数据与动作；② 采用组合/slot 模式，让 Header/Rail/Content 作为子组件就近取数，而非由顶层逐个转发；③ 草稿与动作这类跨切面状态收敛到一个 reducer 或 context，避免几十个 setter 层层传递。
P2稳定传给子组件的引用

内联聚合对象与回调在每次渲染都新建，会使下游 React.memo 失效。配合上述 Context 后，对回调使用 useCallback、对聚合对象使用 useMemo；AppLayout 中 permittedRoutes / menuItems 同样建议 memo 化。

6.4 共享包治理（Monorepo）

P1packages/ui：推广复用或精简，避免“名义共享”
证据
ui 包含 13 个组件（PageHeader/StatusBadge/FilterBar/MetricCard 等，仅 361 行），全仓仅约 6 处实际引用；web-admin 内部仍保留大量同类组件。
建议：盘点重复，把 web-admin 中同类的 Header/Badge/FilterBar/Card 替换为共享版并补齐差异；长期无人使用的组件移出共享包。目标是“同类 UI 只有一处实现”。
P1design-tokens 成为唯一样式真相
证据
TSX 中仅 2 处引用 token；存在 23 处硬编码十六进制色值（10 个文件）；主题在 main.tsx 与 AppLayout.tsx 两处 ConfigProvider 分别配置。
建议：颜色/间距/圆角/阴影统一引用 token，清除硬编码；由 token 生成唯一 antd 主题对象并在一处配置；换肤/大字模式也基于 token 派生。
P1提高 SDK 生成覆盖率，收敛手写端点
证据
18 个 api 文件使用生成的 EduGradeApi，29 个仍为纯手写；generated client（158KB）+ types（172KB）已具备完整契约。
建议：优先把高频手写端点（review/papers/capture/exams）纳入 OpenAPI 生成，手写仅保留“跨端点聚合/编排”；并把生成覆盖率纳入 CI 门槛（仓库已有 update-api-route-coverage 等脚本基础）。
P1抽取跨应用共享的 transport / 错误码
证据
desktop-client 的 api/client.ts（6.5KB）、api/userError.ts（3.6KB）与 web-admin 高度同源，属复制后各自演化。
建议：把 transport、错误码映射、通用类型抽到共享包（如 core-client），desktop 端只注入 Tauri/离线队列等差异，修复一处即处处生效。
P2清理空包、明确归属

packages/auth-client 为 0 源文件、shared-types 仅 43 行。建议明确其职责并填充，或合并入相关包，避免空壳长期存在。

6.5 样式方案

P150 个全局 CSS、0 CSS Module，靠人工命名防冲突
证据
web-admin 有 50 个 .css、无 .module.css；main.tsx 集中 import 12+ 个样式；类名采用 BEM 风格（如 .grading-shell）。
建议：新页面统一使用 Vite 原生支持的 CSS Modules（*.module.css）并与组件 co-locate；reset、tokens 等保留全局；存量按模块渐进迁移，避免类名碰撞与“改一处怕影响别处”。
P2收敛 81 处内联样式与两处样式目录
证据
inline style 共 81 处，集中在 ScoringAssuranceWorkspace(20)、AnswerGroupingDrawer(12)、QualityDashboardPage(8)；样式同时存在于 styles/features 与各 features/*。
建议：静态样式移入 class + token，内联仅保留真正动态计算值；样式目录统一并入对应 feature，减少“两处找样式”。

6.6 构建与运行时性能

P1Chunk 粒度过粗，缺少体积分析与预算
证据
vite.config.ts 将整个 antd / recharts / framer-motion 各打成一个 chunk；项目还含 pdfjs、katex 等重依赖。
建议：引入 rollup-plugin-visualizer 建立产物可视化与体积预算；让重依赖（pdfjs/katex/recharts）仅在对应页面懒加载、不进首屏路径；antd 按需随页面拆分，避免首个后台页面即拉取超大 vendor。
P2首屏白屏与资源提示
证据
index.html 在 JS 执行前为空 div，无首屏占位、无 <noscript>。
建议：内联一个轻量品牌/加载占位与 noscript 提示，改善弱网首屏；对关键 chunk 使用 modulepreload，非首屏图片懒加载并给占位。长列表（审计/学生/任务）保持分页或虚拟滚动（已有 ResponsiveTable 基础）。

6.7 工程化与规范

P1Biome 规则集为 none、formatter 关闭
证据
biome.json preset:"none"，仅手动开启少量 correctness/suspicious 规则，未含 a11y 与多数最佳实践；formatter/assist 关闭。
建议：渐进启用 recommended 规则集（先 warn、修复后转 error），打开 formatter 并接入编辑器与提交钩子/CI。统一格式可消除大量无意义 diff，规则也能在提交前兜底 a11y/复杂度问题。
P2固化运行环境与依赖治理
建议：用 .nvmrc 与 package.json engines 固定 Node 版本；定期做依赖漏洞审计；保持现有 CI 分层（ci:web:fast/full）与契约门（OpenAPI/授权/架构边界），这些是明显优势，应继续维护。

6.8 测试

P1覆盖不均：多个 feature 单测为 0
证据
appeals / calibration / dashboard / onboarding / platform-model-config 为 0；question-bank / gold-papers / members / platform 仅 1；共享包 ui、design-tokens 为 0。
建议：优先为纯函数 model/presentation 补测（投入小、回报高、不依赖渲染），再补关键交互与边界（权限、错误、并发）；共享组件因影响面大应至少有渲染+交互测试；按 feature 设差异化覆盖率门槛，避免“一刀切”。
P2测试关注点：以用户行为为主

继续以 Testing Library 的角色/可访问名查询，避免断言内部 state；E2E 保持对核心链路（考试工作区、采集、阅卷）的覆盖，可在视觉用例中补充可访问性断言。

6.9 可访问性 A11y

P1自定义图片查看器与全局快捷键的键盘/ARIA
证据
答案查看器以 pointer 事件驱动拖拽/缩放，工作台注册大量全局键盘快捷键。
建议：确保可聚焦、具 aria-label/role，所有指针操作有等价键盘路径；快捷键避免与浏览器/读屏冲突并提供“查看/关闭快捷键”入口；配合 Biome a11y 规则在提交前检查。
P2对比度、焦点管理与路由朗读

已具备“跳到主要内容”链接、#main-workspace tabIndex 与大字模式，值得保持。建议：核对次要文字在白底的对比度达 WCAG AA；错误提示不仅靠颜色（已用 Alert，保持）；路由切换时把焦点移至主区域并朗读新页面标题。

6.10 多端策略与空壳

P1teacher-portal 为空壳，需“补全或下线”决策
证据
apps/teacher-portal 仅含一个 README，无 package.json/源码。
建议：若教师能力已由 web-admin 的 teacher experience 承担，则在文档说明并考虑移除该空目录；若规划独立端，则补最小可运行骨架。避免目录长期悬空造成范围误解。
P2厘清“一前端多身份”与“独立客户端”的边界

web-admin 已内置 admin/teacher/auditor/student 多 experience，同时又存在独立 student-portal 与 desktop-client。建议明确各端定位（如 desktop 专注离线扫描、student-portal 专注学生场景），避免学生/采集能力在多处重复实现；Tauri 端保持现有最小权限与 CSP（check:security-config）。

7分阶段落地路线图

建议“先低成本高收益 + 定方向，再做结构治理，最后持续打磨”。周期为相对估计，可按团队人力调整。

阶段一 · P0｜约 1–3 周
  • 顺手修复：渲染体副作用、主题单点收敛、首屏占位与 noscript
  • 路由方向决策；用 3–5 个路由做 TanStack 收敛 PoC（component + beforeLoad）
  • 工作台“只读”数据（任务列表/上下文/聚合）迁移至 react-query
  • 建立 bundle 可视化，确认重依赖不进首屏
阶段二 · P1｜约 3–8 周
  • 拆分 Top 巨型组件；用 Context/组合消除 prop drilling
  • 推广共享 ui、design-tokens，清除硬编码色值
  • 抽取跨端 core-client（transport/错误码），收敛 desktop 复制
  • 提高 SDK 生成覆盖率；样式渐进 CSS Modules
  • 启用 Biome recommended + formatter 并接入 CI
